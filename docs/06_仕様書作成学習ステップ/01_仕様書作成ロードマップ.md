# 仕様書作成学習ステップ 01_仕様書作成ロードマップ

この資料は、業務管理システムサンプルの仕様書を題材にして、要件定義書、基本設計書、詳細設計書、テスト仕様書の作り方を学ぶための入口です。

実装を始める前に「何を作るのか」「どのように作るのか」「どう確認するのか」を文書で整理できるようになることを目指します。

## 1. ゴール

この学習ステップのゴールは、次の4種類の仕様書の役割を説明でき、自分でも小さな変更内容を仕様書に落とし込めるようになることです。

| 種類 | 主な問い | このリポジトリの資料 |
| --- | --- | --- |
| 要件定義書 | 何を、なぜ作るのか | [要件定義書](../01_要件定義書/01_概要.md) |
| 基本設計書 | 利用者から見て、どう動くのか | [基本設計書](../02_基本設計書/01_全体構成.md) |
| 詳細設計書 | 実装者が、どの単位でどう作るのか | [詳細設計書](../03_詳細設計書/01_技術構成とルーティング.md) |
| テスト仕様書 | 作ったものを、どう確認するのか | [テスト仕様書](../04_テスト仕様書/01_テスト概要.md) |

仕様書は、上から順番に細かくなります。

```text
要件定義
  ↓ 何を実現したいか
基本設計
  ↓ 画面・API・データとしてどう見せるか
詳細設計
  ↓ Controller・Model・React などでどう実装するか
テスト仕様
  ↓ 期待どおり動くことをどう確認するか
```

## 2. 読む順番

初めて読む場合は、次の順番がおすすめです。

1. このロードマップで、仕様書全体の流れを確認する。
2. [要件定義書の作り方](02_要件定義書の作り方.md) で「何を決めるか」を学ぶ。
3. [基本設計書の作り方](03_基本設計書の作り方.md) で「画面・API・データへ変換する考え方」を学ぶ。
4. [詳細設計書の作り方](04_詳細設計書の作り方.md) で「実装者が迷わない粒度」を学ぶ。
5. [テスト仕様書の作り方](05_テスト仕様書の作り方.md) で「確認観点」を学ぶ。
6. [演習とチェックリスト](06_演習とチェックリスト.md) で、既存資料を使って練習する。

## 3. 仕様書を書くときの基本姿勢

仕様書は、きれいな文章を書くためだけのものではありません。関係者の認識をそろえ、実装やテストで迷わないようにするための道具です。

特に大切なのは、次の3点です。

| 観点 | 説明 |
| --- | --- |
| 誰のために書くか | 利用者、実装者、テスト担当者、レビュー担当者の誰が読むかを意識します。 |
| どこまで決めるか | 今回作る範囲と、今回は作らない範囲を分けます。 |
| 前後の文書とつながるか | 要件、設計、テストが同じ内容を指しているか確認します。 |

## 4. このリポジトリでの学び方

このリポジトリでは、既存の仕様書を「正しい完成例」として読みます。学習中に新しい機能を思いついても、まずは既存仕様がどのように整理されているかを確認します。

例として、顧客管理機能を追う場合は次のように読みます。

| 順番 | 確認する資料 | 見る内容 |
| --- | --- | --- |
| 1 | [機能要件](../01_要件定義書/03_機能要件.md) | 顧客の一覧、登録、編集、削除の要件 |
| 2 | [画面設計](../02_基本設計書/02_画面設計.md) | 顧客管理画面でできる操作 |
| 3 | [APIとデータ設計](../02_基本設計書/04_APIとデータ設計.md) | 顧客APIと関連データ |
| 4 | [API詳細](../03_詳細設計書/02_API詳細.md) | リクエスト、レスポンス、バリデーション |
| 5 | [APIテストケース](../04_テスト仕様書/03_APIテストケース.md) | APIとして確認する内容 |

このように、1つの機能を縦に追うと、仕様書同士の関係が見えやすくなります。

## 5. 学習時の注意

- 仕様書は、最初から完璧に書こうとしなくて大丈夫です。
- まずは箇条書きで、目的、利用者、操作、データ、確認方法を書き出します。
- あいまいな表現を見つけたら、「誰が」「いつ」「何を」「どうなれば成功か」に分けて書き直します。
- 実装の細かいコードは詳細設計書に寄せ、要件定義書には書きすぎないようにします。
- テスト仕様書は最後に作るだけでなく、要件や設計を書いている途中から確認観点を考えます。
