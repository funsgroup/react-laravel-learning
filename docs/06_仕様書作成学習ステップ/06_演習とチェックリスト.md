# 仕様書作成学習ステップ 06_演習とチェックリスト

この資料では、要件定義書、基本設計書、詳細設計書、テスト仕様書をつなげて考える練習をします。

実際の仕様変更は行わず、既存資料を読みながら「どの文書に何を書くか」を確認します。

## 1. 演習の進め方

演習では、1つの機能を選び、次の順番で追いかけます。

1. 要件定義書で、何を実現したいのかを確認する。
2. 基本設計書で、画面、API、データの大枠を確認する。
3. 詳細設計書で、実装単位の具体的な内容を確認する。
4. テスト仕様書で、確認方法を確認する。
5. 足りない観点がないかチェックリストで確認する。

## 2. 演習1: ログイン機能を追う

ログイン機能について、次の資料を順番に確認します。

| 順番 | 資料 | 確認すること |
| --- | --- | --- |
| 1 | [機能要件](../01_要件定義書/03_機能要件.md) | ログイン、ログアウト、ログイン状態確認の要件 |
| 2 | [画面設計](../02_基本設計書/02_画面設計.md) | ログイン画面の役割 |
| 3 | [認証認可とエラー処理](../02_基本設計書/05_認証認可とエラー処理.md) | ログイン必須APIの方針 |
| 4 | [API詳細](../03_詳細設計書/02_API詳細.md) | 認証APIの詳細 |
| 5 | [APIテストケース](../04_テスト仕様書/03_APIテストケース.md) | ログインAPIの確認観点 |

確認したら、次の問いに答えます。

- 正しいメールアドレスとパスワードでログインできることは、どの要件に対応していますか。
- 未ログインで業務APIを呼んだ場合の動きは、どの設計資料に書かれていますか。
- ログアウト後に業務APIを使えないことは、どのテストで確認できそうですか。

## 3. 演習2: 顧客削除の権限を追う

顧客削除は、権限の違いを学ぶのに向いています。

| 順番 | 資料 | 確認すること |
| --- | --- | --- |
| 1 | [機能要件](../01_要件定義書/03_機能要件.md) | 管理者は削除でき、担当者は削除できないこと |
| 2 | [画面設計](../02_基本設計書/02_画面設計.md) | 削除ボタンの表示条件 |
| 3 | [APIとデータ設計](../02_基本設計書/04_APIとデータ設計.md) | 顧客削除API |
| 4 | [Controller設計](../03_詳細設計書/03_Controller設計.md) | 削除時の権限確認 |
| 5 | [画面テストケース](../04_テスト仕様書/04_画面テストケース.md) | 権限による画面表示差 |

確認したら、次の問いに答えます。

- 画面で削除ボタンを隠すだけでは不十分な理由は何ですか。
- `admin` と `staff` の両方でテストする必要がある理由は何ですか。
- 顧客削除時に、紐づく案件やタスクへどのような影響がありますか。

## 4. 演習3: ダッシュボードを追う

ダッシュボードは、複数のデータを集計して表示する機能です。

| 順番 | 資料 | 確認すること |
| --- | --- | --- |
| 1 | [機能要件](../01_要件定義書/03_機能要件.md) | 件数、ステータス別件数、期限間近タスク |
| 2 | [画面設計](../02_基本設計書/02_画面設計.md) | ダッシュボード画面の表示内容 |
| 3 | [APIとデータ設計](../02_基本設計書/04_APIとデータ設計.md) | ダッシュボードAPI |
| 4 | [DBとModel設計](../03_詳細設計書/04_DBとModel設計.md) | 集計元になるテーブル |
| 5 | [APIテストケース](../04_テスト仕様書/03_APIテストケース.md) | 集計結果の確認方法 |

確認したら、次の問いに答えます。

- 期限が7日以内の未完了タスクを判断するには、どのデータが必要ですか。
- ダッシュボードの件数がずれるとしたら、どのテーブルや状態を確認しますか。
- APIテストで集計結果を確認する場合、どのような事前データが必要ですか。

## 5. 演習4: 小さな仕様追加を考える

練習として、「顧客にメモ欄を追加する」という仮の変更を考えます。実際の既存仕様書は変更しません。

各文書には、次のような内容を書くと考えます。

| 文書 | 書くこと |
| --- | --- |
| 要件定義書 | 利用者は顧客ごとにメモを登録・編集できる |
| 基本設計書 | 顧客管理画面にメモ入力欄を追加する |
| 詳細設計書 | `customers` にメモ用カラムを追加し、APIの入力・出力に含める |
| テスト仕様書 | メモを登録・編集でき、一覧や詳細に表示されることを確認する |

この演習で大切なのは、1つの変更が複数の文書に広がることを理解することです。

## 6. 提出前チェックリスト

仕様書を作成・更新したら、提出前に次のチェックを行います。

### 6.1 要件定義書

- [ ] システムや機能の目的が書かれている。
- [ ] 利用者と権限が書かれている。
- [ ] 機能要件が、確認できる単位に分かれている。
- [ ] 非機能要件や制約が書かれている。
- [ ] 今回やらないこと、未決事項が必要に応じて書かれている。

### 6.2 基本設計書

- [ ] 要件を満たす画面や操作が書かれている。
- [ ] 業務フローが分かる。
- [ ] 必要なAPIの大枠が書かれている。
- [ ] 主要なデータ関係が書かれている。
- [ ] 認証認可とエラー処理の方針が書かれている。

### 6.3 詳細設計書

- [ ] APIの入力、出力、バリデーションが書かれている。
- [ ] Controller の処理の流れが分かる。
- [ ] DBのテーブル、カラム、リレーションが分かる。
- [ ] React画面とAPI呼び出しの対応が分かる。
- [ ] 正常系だけでなく、エラーや権限不足も考慮されている。

### 6.4 テスト仕様書

- [ ] 要件に対応するテスト観点がある。
- [ ] APIテストと画面テストの役割が分かれている。
- [ ] 前提条件、操作、期待結果が書かれている。
- [ ] 権限差や入力エラーのテストがある。
- [ ] 回帰観点や不足テストが整理されている。

### 6.5 全体整合性

- [ ] 要件定義、基本設計、詳細設計、テスト仕様で同じ用語を使っている。
- [ ] 要件にある機能が、設計とテストに落ちている。
- [ ] 設計にある機能が、要件から説明できる。
- [ ] テスト対象が、設計内容とずれていない。
- [ ] リンク先の資料が正しい。

## 7. レビュー依頼時の書き方

レビューを依頼するときは、レビュアーが見やすいように、変更内容と確認したことを短く書きます。

例です。

```text
## 変更内容
- 顧客メモ欄追加の要件定義、基本設計、詳細設計、テスト仕様を追記しました。

## 確認したこと
- 要件IDとテスト観点が対応していることを確認しました。
- 顧客管理画面、顧客API、customers テーブルの記述がつながることを確認しました。

## 特に見てほしいこと
- メモ欄の入力制限が妥当か。
- 画面テストとAPIテストの観点に不足がないか。
```

レビュー依頼では、「全部見てください」だけでなく、特に迷っている点や確認してほしい点を書くと、よいフィードバックをもらいやすくなります。
