# 仕様書作成学習ステップ 04_詳細設計書の作り方

詳細設計書は、基本設計で決めた内容を、実装者が迷わず作業できる粒度まで具体化する文書です。

ここでは、業務管理システムサンプルの [詳細設計書](../03_詳細設計書/01_技術構成とルーティング.md) を題材に説明します。

## 1. 詳細設計書の役割

詳細設計書では、画面、API、Controller、Model、DB、初期データなど、実装に近い情報を書きます。

| 基本設計 | 詳細設計 |
| --- | --- |
| 顧客登録APIを用意する | `POST /api/customers` の入力項目、バリデーション、レスポンスを書く |
| 顧客、案件、タスクを保存する | テーブル、カラム、リレーション、削除時の動作を書く |
| React画面からAPIを呼ぶ | APIクライアント、状態管理、画面更新方針を書く |

詳細設計書の目的は、実装者が「どのファイルに、どの処理を、どの条件で作るか」を判断しやすくすることです。

このリポジトリでは、次の資料が詳細設計書にあたります。

## 2. 作成手順

### 2.1 技術構成とルーティングを書く

まず、実装で使う主要な技術とルートの方針を書きます。

例です。

| 対象 | 書く内容 |
| --- | --- |
| Laravel | APIルート、Middleware、Sanctum の扱い |
| React | 画面ルーティング、API呼び出しの入口 |
| MySQL | 保存する主要テーブル |

ルーティングでは、どのURLにどの処理を割り当てるかを明確にします。基本設計ではAPI一覧だけでもよいですが、詳細設計では認証の有無やControllerの対応まで見えると実装しやすくなります。

### 2.2 API詳細を書く

API詳細では、リクエストとレスポンスを具体的に書きます。

最低限、次の項目を整理します。

| 項目 | 説明 |
| --- | --- |
| メソッド | `GET`、`POST`、`PUT`、`DELETE` など |
| パス | `/api/customers` など |
| 認証 | ログインが必要か |
| リクエスト | 送信する項目 |
| レスポンス | 返す項目 |
| バリデーション | 入力値の必須、型、最大文字数など |
| エラー | 失敗時の主なステータス |

例です。

```text
POST /api/customers

目的:
顧客を新規登録する。

主な入力:
- name
- status
- email
- phone

主な確認:
- name は必須
- status は決められた値だけ許可する
- 登録後、作成した顧客情報を返す
```

API詳細は、フロントエンドとバックエンドの約束です。ここがあいまいだと、React と Laravel の実装がずれやすくなります。

### 2.3 Controller設計を書く

Controller設計では、APIを受け取った後の処理の流れを書きます。

例です。

```text
顧客登録
  1. ログイン済みか確認する
  2. 入力値をバリデーションする
  3. customers テーブルに登録する
  4. 登録した顧客情報をJSONで返す
```

Controller設計で大切なのは、正常系だけでなく失敗する場合も書くことです。

| 失敗例 | 考えること |
| --- | --- |
| 未ログイン | 認証エラーにする |
| 入力が不正 | バリデーションエラーにする |
| 権限がない | 認可エラーにする |
| 対象データがない | Not Found として扱う |

### 2.4 DBとModel設計を書く

DBとModel設計では、保存するデータの形と関係を書きます。

このリポジトリでは、主に次の関係があります。

```text
users
  ├─ projects.owner_id
  └─ tasks.assignee_id

customers
  └─ projects.customer_id
        └─ tasks.project_id
```

書く内容の例です。

| 項目 | 説明 |
| --- | --- |
| テーブル | `customers`、`projects`、`tasks` など |
| カラム | 保存する項目 |
| リレーション | 顧客と案件、案件とタスクの関係 |
| 削除時の動作 | 親データ削除時に子データをどう扱うか |
| 初期値 | ステータスなどの初期値 |

DB設計では、削除時の動作を忘れやすいです。顧客を削除したときに案件も削除するのか、残すのかを決めておきます。

### 2.5 React詳細設計を書く

React詳細設計では、画面コンポーネント、状態、API呼び出し、エラー表示の方針を書きます。

例です。

| 観点 | 書く内容 |
| --- | --- |
| 画面状態 | 一覧データ、入力中のフォーム、読み込み中、エラー |
| API呼び出し | どの操作でどのAPIを呼ぶか |
| 表示制御 | `admin` だけ削除ボタンを表示する |
| 更新方法 | 登録や削除後に一覧を再取得するか |

詳細設計では、利用者から見える画面と、APIのやり取りがつながっているかを確認します。

### 2.6 初期データ設計を書く

初期データ設計では、開発や学習を始めた直後に必要なデータを書きます。

このリポジトリでは、管理者と担当者の初期ユーザーがあります。

| 権限 | メールアドレス | 用途 |
| --- | --- | --- |
| 管理者 | `admin@example.com` | 削除操作を確認する |
| 担当者 | `staff@example.com` | 削除できないことを確認する |

初期データは、画面確認やテストの土台になります。権限差を確認するためのユーザーは、特に重要です。

## 3. 実装者が迷わない粒度

詳細設計は、細かければよいというものではありません。重要なのは、実装者が判断に迷う部分を先に決めておくことです。

| 迷いやすいこと | 詳細設計で決める内容 |
| --- | --- |
| どの入力を必須にするか | バリデーション |
| どのステータス値を使うか | 許可する保存値 |
| 削除権限をどこで見るか | Controller や Policy の方針 |
| 一覧に関連データを含めるか | レスポンス項目 |
| 親データ削除時に子データをどうするか | 外部キー制約や削除方針 |

実装者が選択できてしまう箇所が多いほど、人によって実装がずれます。詳細設計は、そのずれを減らすためにあります。

## 4. 初心者がつまずきやすい点

| つまずき | 改善方法 |
| --- | --- |
| APIの入力だけを書いてレスポンスを書かない | React が何を受け取るかまで書く |
| 正常系だけを書く | 未ログイン、権限不足、入力エラーも書く |
| DBの親子関係を書かない | リレーションと削除時の動作を書く |
| 画面とAPIの対応がずれる | ボタンやフォームごとに呼ぶAPIを確認する |
| 詳細設計に要件の理由を書きすぎる | 理由は要件定義、実装判断は詳細設計に分ける |

## 5. ミニテンプレート

新しいAPIや画面の詳細設計を書くときは、次の形で下書きします。

```text
## 機能名

### ルート・API
- メソッド
- パス
- 認証の有無
- Controller

### 入力
- 項目名
- 必須かどうか
- 型
- バリデーション

### 出力
- 返すJSON
- 関連データを含めるか

### 処理の流れ
- 正常系
- 入力エラー
- 権限エラー
- データが存在しない場合

### DB / Model
- テーブル
- カラム
- リレーション
- 削除時の動作

### React
- 表示する項目
- 操作
- API呼び出し
- エラー表示
```

このテンプレートを使うと、実装前に考えるべきことを漏らしにくくなります。
