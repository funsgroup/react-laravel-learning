# 仕様書作成学習ステップ 03_基本設計書の作り方

基本設計書は、要件定義で決めた「何を作るか」を、画面、業務フロー、API、データ、認証認可、エラー処理に落とし込む文書です。

ここでは、業務管理システムサンプルの [基本設計書](../02_基本設計書/01_全体構成.md) を題材に説明します。

## 1. 基本設計書の役割

基本設計書は、利用者から見える動きと、システム全体の大きな構造を決めます。

| 要件定義 | 基本設計 |
| --- | --- |
| 顧客を新規登録できる | 顧客管理画面に登録フォームを用意する |
| ダッシュボードで件数を確認できる | ダッシュボード画面に顧客数、案件数、未完了タスク数を表示する |
| 未ログイン利用者は業務APIを利用できない | 業務APIはログイン必須にする |

基本設計書では、まだ Controller のメソッド名や DB カラムの細かい型までは書きすぎません。実装の細部は詳細設計書で扱います。

このリポジトリでは、次の資料が基本設計書にあたります。

- [01_全体構成](../02_基本設計書/01_全体構成.md)
- [02_画面設計](../02_基本設計書/02_画面設計.md)
- [03_業務フロー](../02_基本設計書/03_業務フロー.md)
- [04_APIとデータ設計](../02_基本設計書/04_APIとデータ設計.md)
- [05_認証認可とエラー処理](../02_基本設計書/05_認証認可とエラー処理.md)

## 2. 作成手順

### 2.1 全体構成を書く

最初に、システムを構成する大きな部品を書きます。

このリポジトリでは、React、Laravel、MySQL、Docker Compose が主な構成要素です。

```text
ブラウザ
  ↓ HTTP / Cookie
React + Vite
  ↓ fetch API
Laravel API + Sanctum
  ↓ Eloquent ORM
MySQL
```

全体構成を書くと、どの処理をどの層が担当するかが分かりやすくなります。

| 層 | 担当すること |
| --- | --- |
| React | 画面表示、フォーム入力、API呼び出し |
| Laravel | 認証、認可、業務API、入力チェック |
| MySQL | ユーザー、顧客、案件、タスクの保存 |

### 2.2 画面設計を書く

画面設計では、利用者が見る画面と、その画面でできる操作を書きます。

例です。

| 画面 | 概要 | 主な操作 |
| --- | --- | --- |
| ログイン画面 | メールアドレスとパスワードでログインする | ログイン |
| 顧客管理 | 顧客情報を管理する | 一覧、登録、編集、削除 |
| タスク管理 | 案件に紐づくタスクを管理する | 一覧、登録、編集、削除 |

画面設計では、利用者の操作を中心に書きます。例えば「削除ボタンは `admin` だけ表示する」のような権限に関する表示条件も、ここで書いておくと実装者が迷いにくくなります。

### 2.3 業務フローを書く

業務フローは、利用者の操作がどの順番で進むかを表します。

文章だけでは分かりにくい場合は、次のような簡単な流れで十分です。

```text
ログイン
  ↓
顧客を登録
  ↓
顧客に紐づく案件を登録
  ↓
案件に紐づくタスクを登録
  ↓
ダッシュボードで状況を確認
```

業務フローを書くと、画面同士のつながりや、データの前後関係が見えます。たとえば、案件は顧客に紐づくため、案件登録より前に顧客が必要です。

### 2.4 APIとデータの大枠を書く

基本設計では、APIの一覧と、主要なデータの関係を書きます。

例です。

| メソッド | パス | 概要 |
| --- | --- | --- |
| GET | `/api/customers` | 顧客一覧を返す |
| POST | `/api/customers` | 顧客を登録する |
| DELETE | `/api/customers/{customer}` | 顧客を削除する |

データ関係は、最初はシンプルな図で十分です。

```text
customers
  └─ projects
        └─ tasks
```

この段階では、すべてのカラムやバリデーションを書ききる必要はありません。詳細は詳細設計書に分けます。

### 2.5 認証認可とエラー処理を書く

認証は「ログインしているか」、認可は「その操作をしてよいか」です。

このリポジトリでは、次のように整理できます。

| 観点 | 内容 |
| --- | --- |
| 認証 | 業務APIはログイン必須 |
| 認可 | 削除は `admin` のみ |
| 入力エラー | バリデーションエラーは 422 |
| 未ログイン | 認証エラーとして扱う |
| 権限不足 | 権限エラーとして扱う |

エラー処理を基本設計に書くと、画面側の表示やAPI側のレスポンス方針がそろいます。

## 3. 要件から基本設計へ変換する例

要件定義の `FR-CUS-004` と `FR-CUS-005` を例にします。

| 要件 | 基本設計で決めること |
| --- | --- |
| 管理者は顧客を削除できる | 顧客管理画面に削除操作を用意する |
| 担当者は顧客を削除できない | `staff` では削除ボタンを表示しない |
| 管理者は顧客を削除できる | `DELETE /api/customers/{customer}` を用意する |
| 担当者は顧客を削除できない | API側でも削除権限を確認する |

画面でボタンを隠すだけでは不十分です。APIを直接呼ばれる可能性があるため、Laravel側でも認可が必要です。

## 4. 初心者がつまずきやすい点

| つまずき | 改善方法 |
| --- | --- |
| 画面だけを書いてAPIを書かない | 画面操作ごとに必要なAPIを確認する |
| APIだけを書いて画面の使い方を書かない | 利用者がどこから操作するかを書く |
| データの親子関係を書かない | 顧客、案件、タスクの関係を図にする |
| 権限を画面だけで考える | 画面とAPIの両方で認可を考える |
| 詳細を書きすぎる | カラム型やController処理は詳細設計へ分ける |

## 5. ミニテンプレート

新しい機能の基本設計を書くときは、次の形で下書きします。

```text
## 機能名

### 画面
- どの画面に表示するか
- 利用者ができる操作
- 権限による表示差

### 業務フロー
- 操作の順番
- 前提となるデータ
- 完了条件

### API
- メソッド
- パス
- 概要
- 認証が必要か

### データ
- 主なテーブル
- データ同士の関係

### 認証認可・エラー
- 誰が操作できるか
- 失敗時にどう扱うか
```

このテンプレートは、詳細設計を書く前の地図として使います。
