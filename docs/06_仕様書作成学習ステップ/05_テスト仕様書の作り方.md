# 仕様書作成学習ステップ 05_テスト仕様書の作り方

テスト仕様書は、要件や設計どおりに動くことを確認するための文書です。

ここでは、業務管理システムサンプルの [テスト仕様書](../04_テスト仕様書/01_テスト概要.md) を題材に説明します。

## 1. テスト仕様書の役割

テスト仕様書では、「何を確認すれば完成と言えるか」を整理します。

| 元になる文書 | テストで確認すること |
| --- | --- |
| 要件定義書 | 利用者が必要な操作をできるか |
| 基本設計書 | 画面、API、認証認可が設計どおりか |
| 詳細設計書 | バリデーション、レスポンス、DB更新が実装どおりか |

このリポジトリでは、次の資料がテスト仕様書にあたります。

- [01_テスト概要](../04_テスト仕様書/01_テスト概要.md)
- [02_既存自動テスト](../04_テスト仕様書/02_既存自動テスト.md)
- [03_APIテストケース](../04_テスト仕様書/03_APIテストケース.md)
- [04_画面テストケース](../04_テスト仕様書/04_画面テストケース.md)
- [05_回帰観点と不足テスト](../04_テスト仕様書/05_回帰観点と不足テスト.md)

## 2. 作成手順

### 2.1 テスト方針を書く

最初に、どの範囲をどの方法で確認するかを書きます。

例です。

| 種類 | 確認すること |
| --- | --- |
| APIテスト | 認証、入力チェック、DB更新、レスポンス |
| 画面テスト | 表示、フォーム操作、権限による表示差 |
| 回帰確認 | 既存機能が壊れていないか |

このリポジトリは `backend/` を学習者が作る状態です。そのため、Laravel の自動テストは `backend/` 作成後に実装・実行します。

### 2.2 要件からテスト観点を作る

テストは、要件定義から作ります。

例です。

| 要件 | テスト観点 |
| --- | --- |
| 利用者はログインできる | 正しいメールアドレスとパスワードでログインできる |
| 未ログイン利用者は業務APIを利用できない | 未ログインで顧客一覧APIを呼ぶと拒否される |
| 管理者は顧客を削除できる | `admin` で顧客削除APIが成功する |
| 担当者は顧客を削除できない | `staff` で顧客削除APIが拒否される |

要件IDがある場合は、テストケースにも要件IDを書いておくと追跡しやすくなります。

### 2.3 APIテストケースを書く

APIテストでは、Laravel API が設計どおりに動くかを確認します。

書く項目の例です。

| 項目 | 説明 |
| --- | --- |
| ケースID | テストを識別する番号 |
| 対象API | メソッドとパス |
| 前提条件 | ログイン状態、権限、事前データ |
| 入力 | リクエスト内容 |
| 期待結果 | ステータス、レスポンス、DB状態 |

例です。

```text
ケース:
管理者は顧客を削除できる。

前提:
admin でログインしている。
削除対象の顧客が存在する。

操作:
DELETE /api/customers/{customer} を呼ぶ。

期待結果:
削除が成功する。
対象顧客が一覧に表示されない。
```

APIテストでは、画面を使わずに直接APIを確認します。これにより、画面の不具合とAPIの不具合を切り分けやすくなります。

### 2.4 画面テストケースを書く

画面テストでは、利用者がブラウザで操作したときの動きを確認します。

書く項目の例です。

| 項目 | 説明 |
| --- | --- |
| 対象画面 | ログイン、顧客管理、案件管理など |
| 前提条件 | ログインユーザー、事前データ |
| 操作手順 | クリック、入力、保存など |
| 期待結果 | 表示、メッセージ、一覧更新など |

例です。

```text
ケース:
担当者では削除ボタンが表示されない。

前提:
staff@example.com でログインしている。
顧客データが存在する。

操作:
顧客管理画面を開く。

期待結果:
顧客一覧は表示される。
削除ボタンは表示されない。
```

画面テストでは、利用者が実際に見る表示を確認します。APIテストと組み合わせることで、見た目とサーバー側の両方を確認できます。

### 2.5 回帰観点を書く

回帰とは、変更によって以前動いていた機能が壊れることです。

回帰観点では、新しい変更を入れたときに壊れやすい場所を書きます。

例です。

| 変更内容 | 回帰確認 |
| --- | --- |
| 認証処理を変更した | ログイン、ログアウト、ログイン状態復元を確認する |
| 顧客APIを変更した | 案件一覧で顧客名が表示されるか確認する |
| 削除権限を変更した | `admin` と `staff` の両方で削除操作を確認する |

回帰観点は、テスト漏れを減らすためのメモです。すべてを毎回手作業で確認するのは大変なので、自動テストにできるものは自動テストへ寄せます。

## 3. 要件・設計・テストをつなげる

テスト仕様書は、単独で作るものではありません。必ず要件や設計と対応させます。

| 要件ID | 設計 | テスト |
| --- | --- | --- |
| FR-CUS-001 | 顧客管理画面、`GET /api/customers` | 顧客一覧が表示される |
| FR-CUS-002 | 顧客登録フォーム、`POST /api/customers` | 顧客を登録できる |
| FR-CUS-004 | 削除ボタン、削除API | 管理者で削除できる |
| FR-CUS-005 | 権限による表示制御、API認可 | 担当者で削除できない |

この対応が取れていない場合、要件はあるのに確認されていない機能が生まれます。

## 4. 初心者がつまずきやすい点

| つまずき | 改善方法 |
| --- | --- |
| 正常系だけ確認する | 入力エラー、未ログイン、権限不足も確認する |
| 画面だけ確認する | APIテストも用意する |
| テストの前提が書かれていない | ログインユーザーや事前データを書く |
| 期待結果があいまい | ステータス、表示、DB状態など確認できる形で書く |
| 要件との対応が分からない | 要件IDや設計資料への参照を書く |

## 5. ミニテンプレート

テストケースを書くときは、次の形で下書きします。

```text
## テストケース名

### 対応する要件・設計
- 要件ID:
- 関連する設計:

### 前提条件
- ログインユーザー:
- 事前データ:

### 操作
1. 何をするか
2. 次に何をするか

### 期待結果
- 画面表示:
- APIレスポンス:
- DB状態:
- エラー表示:

### 補足
- 手動確認か自動テストか
- 回帰確認で特に見ること
```

期待結果は、テスト担当者が同じ結果を判断できるように書きます。
