# 仕様書作成学習ステップ 02_要件定義書の作り方

要件定義書は、「何を作るのか」と「なぜ作るのか」を整理する文書です。

ここでは、業務管理システムサンプルの [要件定義書](../01_要件定義書/01_概要.md) を題材に、初心者が迷いやすいポイントを順番に説明します。

## 1. 要件定義書の役割

要件定義書では、まだ Controller 名やテーブル定義のような実装の細部までは決めません。利用者や業務の視点で、システムに必要なことを整理します。

| 書くこと | 目的 |
| --- | --- |
| システムの目的 | なぜこのシステムが必要なのかを共有するため |
| 利用者 | 誰が使うシステムなのかを明確にするため |
| 対象業務 | どの業務を助けるのかを決めるため |
| 機能要件 | システムができるべきことを決めるため |
| 非機能要件 | 性能、セキュリティ、運用などの条件を決めるため |
| 制約・対象外 | 今回やらないことを明確にするため |

このリポジトリでは、次の資料が要件定義書にあたります。

- [01_概要](../01_要件定義書/01_概要.md)
- [02_利用者と対象業務](../01_要件定義書/02_利用者と対象業務.md)
- [03_機能要件](../01_要件定義書/03_機能要件.md)
- [04_非機能要件と制約](../01_要件定義書/04_非機能要件と制約.md)

## 2. 作成手順

### 2.1 目的を書く

最初に、システムの目的を書きます。目的は「機能の一覧」ではなく、「利用者が何に困っていて、何を改善したいのか」です。

このリポジトリでは、顧客、案件、タスクを一元管理することが目的です。

良い書き方の例です。

```text
営業・業務担当者が顧客情報、案件情報、案件に紐づくタスクを一元管理できるようにする。
```

避けたい書き方の例です。

```text
React と Laravel で CRUD を作る。
```

技術は大切ですが、要件定義では「利用者にとって何が良くなるか」を先に書きます。

### 2.2 利用者と権限を書く

次に、誰が使うかを書きます。利用者ごとにできることが違う場合は、権限も整理します。

このリポジトリでは、`admin` と `staff` があります。

| 権限 | できることの例 |
| --- | --- |
| `admin` | 登録、編集、削除ができる |
| `staff` | 登録、編集はできるが、削除はできない |

権限を書くときは、「誰ができるか」だけでなく「誰ができないか」も書きます。できないことを書いておくと、後で基本設計やテスト仕様に落とし込みやすくなります。

### 2.3 対象業務を書く

対象業務は、システムで扱う仕事の範囲です。

このリポジトリでは、主に次の業務を対象にします。

- 顧客情報の管理
- 顧客に紐づく案件の管理
- 案件に紐づくタスクの管理
- 件数や期限間近タスクの確認

対象業務を書くときは、業務で使う言葉を優先します。実装都合の言葉だけで書くと、利用者やレビュー担当者が理解しにくくなります。

### 2.4 機能要件を書く

機能要件は、システムができるべきことです。

このリポジトリでは、`FR-CUS-001` のように要件IDを付けています。要件IDを付けると、設計書やテスト仕様書から参照しやすくなります。

| 要件ID | 要件 |
| --- | --- |
| FR-CUS-001 | 顧客一覧を表示できる。 |
| FR-CUS-002 | 顧客を新規登録できる。 |
| FR-CUS-004 | 管理者は顧客を削除できる。 |
| FR-CUS-005 | 担当者は顧客を削除できない。 |

書き方のコツは、1つの要件に複数の意味を詰め込みすぎないことです。

良い例です。

```text
管理者は顧客を削除できる。
担当者は顧客を削除できない。
```

避けたい例です。

```text
顧客管理をいい感じに行える。
```

「いい感じ」は、人によって解釈が変わります。仕様書では、確認できる言葉に分けて書きます。

### 2.5 非機能要件と制約を書く

非機能要件は、機能そのものではなく、品質や条件に関する要件です。

例です。

- 認証が必要なAPIは、未ログインでは利用できない。
- 開発環境は Docker Compose で起動する。
- 学習用サンプルのため、本番運用向けの監査ログは対象外にする。

制約は「今回の前提」です。制約を書くことで、読んだ人が過度な期待をしないようにできます。

## 3. 要件定義書から次の文書へつなげる

要件定義書を書いたら、次に基本設計書へ落とし込みます。

| 要件定義で書いたこと | 基本設計で決めること |
| --- | --- |
| 顧客一覧を表示できる | 顧客管理画面に何を表示するか |
| 顧客を登録できる | 登録フォーム、入力項目、登録API |
| 管理者だけ削除できる | 削除ボタンの表示条件、削除APIの認可 |
| 期限が7日以内のタスクを表示できる | ダッシュボードの表示内容、集計API |

要件定義書は、後続の設計書の出発点です。後から基本設計や詳細設計を書いたとき、要件定義に戻って「この設計はどの要件を満たすためのものか」を確認します。

## 4. 初心者がつまずきやすい点

| つまずき | 改善方法 |
| --- | --- |
| 技術名から書き始める | まず利用者と業務の困りごとを書く |
| 1文が大きすぎる | 一覧、登録、編集、削除のように操作単位へ分ける |
| 対象外を書かない | 今回作らない機能も明記する |
| 権限差を書き忘れる | できる人、できない人を両方書く |
| テストできない表現になる | 画面やAPIで確認できる表現に直す |

## 5. ミニテンプレート

新しい機能の要件定義を書くときは、最初に次の形で下書きします。

```text
## 機能名

### 目的
この機能で、誰のどの作業を楽にするかを書く。

### 利用者
この機能を使う権限や利用者を書く。

### 機能要件
- 利用者は、○○を一覧表示できる。
- 利用者は、○○を登録できる。
- 利用者は、○○を編集できる。
- 管理者は、○○を削除できる。
- 担当者は、○○を削除できない。

### 非機能要件・制約
- ログイン済み利用者だけが利用できる。
- 今回は○○画面は対象外にする。

### 未決事項
- まだ決まっていない内容を書く。
```

未決事項は、悪いものではありません。決まっていないことを隠すより、見える場所に置くほうが安全です。
